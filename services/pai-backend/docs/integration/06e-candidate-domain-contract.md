# INTEGRATION-06E Candidate Domain Contract

## Status

Proposed PAI-owned domain boundary for `INTEGRATION-06E.0`. This is not an
implementation or persistence schema.

## Candidate aggregate

```text
Candidate (PAI-owned aggregate)
  candidate_id: UUID       # stable business identity; never a workflow ID
  organization_id: UUID
  status: CandidateStatus
  review_state: CandidateReviewState
  created_at / updated_at
  primary_document_ref: CandidateDocumentRef | null

  Documents
    candidate_document_id
    document_ref (opaque PAI reference)
    kind: CV | supporting_document
    is_primary
    attached_at

  Extraction Jobs
    job_ref (internal/opaque workflow reference)
    candidate_document_id
    status / error summary

  Profiles
    profile_ref (opaque profile-version reference)
    version
    review_state
    is_current_review_subject

  Claims
    claim_id: UUID       # stable within the candidate read model
    profile_ref/version
    value / evidence_type / context / review status
    evidence_refs

  Evidence
    evidence_id: UUID
    claim_id
    source document reference
    source locator/span and policy-approved excerpt

  Review State
    current profile version
    reviewer decision and audit reference
    revision/rejection reason summary
```

## Identity rules

The following mappings are forbidden:

```text
document_id == candidate_id
profile_id  == candidate_id
job_id      == candidate_id
```

Those IDs identify technical resources. `candidate_id` is generated by PAI
when a Candidate aggregate is created and remains stable across document
replacement, extraction retries, profile corrections, and profile versions.

`claim_id` is also an opaque domain identifier. A claim may be re-projected
when a profile is corrected; the projection must retain its source profile
version and provenance rather than silently reusing a technical array index.

## Status and review lifecycle

```text
CandidateStatus:
  ACTIVE -> ARCHIVED

CandidateReviewState:
  DRAFT
    -> EXTRACTION_PENDING
    -> PENDING_REVIEW
    -> ACCEPTED
    -> NEEDS_REVISION -> PENDING_REVIEW
    -> REJECTED
```

`CandidateStatus` expresses aggregate availability. `CandidateReviewState`
expresses the review subject and must not be inferred solely from a job's
technical status. A candidate can remain `ACTIVE` while its latest profile
version is `NEEDS_REVISION`, provided PAI policy defines which previously
accepted profile remains current; that policy must be explicit in the future
implementation.

Profile-level transitions remain the source of truth for reviewer actions:

```text
PENDING_REVIEW | CORRECTED
  -> ACCEPTED | NEEDS_REVISION | REJECTED
```

The Candidate read model summarizes these transitions and keeps the underlying
profile version for auditability.

## Ownership and boundaries

### PAI owns

- candidate identity and organization scope;
- candidate documents and their source references;
- extraction orchestration and profile versions;
- claim normalization, evidence, locators, and provenance;
- review state and reviewer actions;
- authorization decisions for candidate and evidence access.

### LMS owns

- user authentication and session UX;
- candidate-review screens and client-side presentation state;
- training delivery and learner progress;
- calling PAI through the future `PaiLearningAdapter`.

The LMS is a consumer of this aggregate, not its owner. It must not persist a
second candidate identity or use a document/profile/job ID as a substitute.

## Aggregate invariants for 06E.1

1. A Candidate belongs to exactly one organization.
2. A candidate document can only be attached to a document owned by the same
   organization and must preserve the document's storage identity.
3. Every exposed claim belongs to one candidate and one profile version.
4. Every evidence reference belongs to an exposed claim and resolves through
   PAI authorization.
5. A review action requires an expected profile version and an actor resolved
   by PAI; browser-supplied actor IDs are not accepted.
6. Removing or expiring a document must not rewrite historical profile/audit
   identity; retrieval returns the policy-defined unavailable state.
7. Raw CV/JD content is not copied into Candidate metadata or audit records.

## Non-goals for 06E.0

- no SQLAlchemy model or Alembic migration;
- no LMS repository changes;
- no React/FE contract implementation;
- no candidate-to-user identity inference;
- no capability-analysis or learning-path behavior changes.
